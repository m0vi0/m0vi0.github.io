Catching Deauth Floods: A Homemade WiFi IDS Feeding Wazuh

KismetWazuhSyslogWIDS

Many home networks lack visibility into local wireless activity. A deauthentication attack — which forces devices to disconnect so their reassociation can be captured — often goes unnoticed by consumer routers. Wazuh was already deployed as the homelab SIEM, so the objective here was to forward meaningful WiFi IDS alerts into the existing security pipeline rather than leaving them siloed in a separate dashboard.

The setup

A Raspberry Pi 3B+ already sits on my home network as a subnet router, so I put Kismet on it in monitor mode with a dedicated WiFi adapter, purely for detection rather than device inventory. 

# put the adapter into monitor mode
airmon-ng check kill
airmon-ng start wlan1

# run kismet against the monitor interface
kismet -c wlan1mon

Kismet ships with a built-in alert type for exactly this scenario — DEAUTHFLOOD, which fires when it sees an abnormal rate of deauthentication frames from a source. The throttle is configurable in kismet_site.conf, so it doesn't fire on every single disconnect a client legitimately sends: 

# kismet_site.conf
alert=DEAUTHFLOOD,5/min,1/sec

Getting alerts out of Kismet

Kismet's alerts live in its own REST endpoint and web UI, not in syslog by default, so they never reach Wazuh on their own. Rather than patch Kismet itself, I wrote a small poller that watches /alerts/views/all/alerts.json for new entries and forwards each one to the local syslog, which the Wazuh agent already collects from. 

import requests, syslog, time

KISMET_URL = "http://127.0.0.1:2501/alerts/views/all/alerts.json"
seen = set()

syslog.openlog("kismet-alert", facility=syslog.LOG_LOCAL0)

while True:
    # Use a secure credential store or environment variable for the password
    resp = requests.get(KISMET_URL, auth=("admin", ""))
    for alert in resp.json():
        alert_id = alert.get("kismet.alert.timestamp")
        if alert_id not in seen:
            seen.add(alert_id)
            msg = f"KISMET_ALERT type={alert.get('kismet.alert.class')} " \
                  f"text={alert.get('kismet.alert.text')}"
            syslog.syslog(syslog.LOG_WARNING, msg)
    time.sleep(5)

For production use, run the poller under a service manager (for example, a systemd unit) and store any credentials securely (environment variables or a secrets store rather than hard-coding them).

Writing the Wazuh rule

The stock Wazuh ruleset has no idea what a Kismet alert looks like, so this needed a custom decoder and rule in local_rules.xml — a decoder to parse the forwarded syslog tag, and a rule to fire on it. 

<!-- local_decoder.xml -->
<decoder name="kismet-alert">
  <prematch>KISMET_ALERT</prematch>
</decoder>

<decoder name="kismet-alert-type">
  <parent>kismet-alert</parent>
  <regex>type=(\S+) text=(.+)</regex>
  <order>alert_type, alert_text</order>
</decoder>
<!-- local_rules.xml -->
<group name="kismet,wireless,">
  <rule id="100201" level="10">
    <decoded_as>kismet-alert</decoded_as>
    <field name="alert_type">DEAUTHFLOOD</field>
    <description>WiFi deauthentication flood detected by Kismet</description>
    <mitre>
      <id>T1499</id>
    </mitre>
  </rule>
</group>

Tuning out the noise

Raw deauth events are noisier than they look at first — normal WiFi roaming generates legitimate deauth/reassociation frames as devices move between APs or drop and reconnect on a weak signal, and a naive rule that alerts on any deauth frame at all will bury a real attack in false positives within a day. Kismet's own DEAUTHFLOOD throttle (rate-per-source rather than raw frame count) does most of the filtering before the alert ever reaches Wazuh, but it's still worth tuning the rate threshold against your own network's baseline rather than trusting the default — a house full of IoT devices on weak WiFi looks very different from a quiet network with two laptops.

Getting notified

Alerts route through the Postfix relay already configured for the rest of the homelab, so a real deauth flood shows up as an email rather than a line sitting in a dashboard nobody's watching in real time.

What I'd do differently

Polling Kismet's alert endpoint every few seconds works, but it's not elegant — Kismet's newer versions support a websocket event stream, which would push alerts the moment they fire instead of introducing a five-second polling lag. That's the next iteration: swap the poller for a persistent websocket listener so detection-to-alert latency drops from seconds to effectively real time.
