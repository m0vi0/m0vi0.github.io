Resilient home network with automatic failover

TailscaleUptime KumaWazuhFailover

This began with a practical constraint: there was no administrative access to the home router. Without port forwarding or VLAN configuration at the router level, remote access to devices had to be achieved by routing around the limitation rather than changing the network infrastructure itself.

Step one: get devices reachable at all

The initial approach was to make individual devices reachable remotely by placing them on a VPN so router configuration would not be required. Tailscale was chosen for this purpose: it provides a WireGuard-based mesh overlay that allows devices to be reachable across the internet without direct router changes.

Reaching the rest of the LAN without a VPN client on everything

That worked for the handful of devices I could actually install Tailscale on, but home automation gear doesn't run a VPN client. To reach that without touching every device individually, I set up one node as a Tailscale subnet router — a single machine that advertises routes to the rest of the home LAN, so any device on the tailnet can reach anything on that subnet without being on the network directly. 

# on the subnet router node
tailscale up --advertise-routes=192.168.1.0/24 --accept-routes

# approve the route from the Tailscale admin console
# (or via tailscale CLI on a node with admin rights)

Removing the single point of failure

One subnet router is a single point of failure — if that node goes down, remote access to the entire home network goes down with it. Tailscale supports multiple nodes advertising the same subnet routes with automatic failover between them, so I added two more nodes doing the same thing. If the primary drops, the tailnet routes through one of the others without any manual intervention.

Monitoring the monitors

Having three router nodes is only useful if I actually know when one of them dies. A single monitoring instance would just move the single point of failure one layer up, so I ran two Uptime Kuma instances instead, each watching three of the other nodes — and each watching the other Uptime Kuma instance too. If one monitor goes down, the other one is still watching everything, including the fact that its counterpart is down.

Layering security monitoring on top

With the network layer stable, I brought Wazuh in as a SIEM across those same three nodes for actual security visibility — not just "is it up," but "is anything on it behaving strangely." Kismet runs on one node with a WiFi adapter in monitor mode, watching for deauthentication floods and piping alerts into Wazuh over syslog. Frigate runs alongside with motion detection, so the same infrastructure that keeps remote access alive is also the thing watching over the physical space it's protecting.

What I'd do differently

The failover routing and the failover monitoring were both good calls, but I built them as two separate decisions rather than one designed system — if I were doing this from scratch, I'd map out every single point of failure across the whole stack up front (routing, monitoring, alerting, the SIEM itself) instead of noticing and patching each one as it became obviously fragile.

Why this matters for security work

This wasn't originally a security project — it started as a workaround for not having router access. But the instinct it forced was one that matters directly in offensive security: think about what happens when a component fails, don't assume the happy path holds, and check your own blind spots before someone else finds them for you.
